# Сервис приёма платежей в USDT

Go-сервис и PostgreSQL реализуют сценарий: счёт → перевод USDT → N подтверждений → AML → зачисление с комиссией либо подготовка возврата. Ethereum и AML моделируются локально; реальные транзакции не отправляются.

Производственная архитектура: [DESIGN.md](DESIGN.md) и [PDF](output/pdf/usdt-payment-design.pdf).

## Запуск и настройки

Нужны Docker и Docker Compose v2. Из корня репозитория:

```bash
docker compose up
```

API — `http://localhost:8080`, PostgreSQL — `127.0.0.1:54329`; порты доступны только локально. Goose применяет встроенные миграции из `migrations/` перед запуском API. Volume `postgres_data` сохраняет данные. После изменения исходников используйте `docker compose up --build`; остановка с сохранением данных — `docker compose down`.

Compose работает без `.env`. Для изменения настроек скопируйте `.env.example` в `.env`. Ключи и пароль по умолчанию предназначены для локальной демонстрации.

| Настройка | По умолчанию | Назначение |
|---|---|---|
| CONFIRMATIONS | 3 | N; положительное целое |
| LOCAL_MOCKS | true | Управляющие маршруты `/mock/*` |
| MOCK_CONTROL_KEY | local-control-key | Отдельный ключ управления |
| AML_BLACKLIST | `0xbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb` | Отправители HIGH, через запятую |
| AML_UNAVAILABLE | false | Недоступность AML при запуске |
| AML_RETRY_INTERVAL | 5s | Повтор после ошибки; минимум 1s |
| REFUNDS_ENABLED | true | Автоматическая подготовка READY |
| REFUND_UNSAFE_SENDERS | пусто | Источники с неподтверждённым маршрутом, через запятую |

| Партнёр | X-API-Key | Комиссия |
|---|---|---|
| alpha | local-alpha-key | 100 bps = 1% |
| beta | local-beta-key | 250 bps = 2,5% |

Ключи задаются через PARTNER_ALPHA_KEY/PARTNER_BETA_KEY; в БД хранятся SHA-256 хеши. Ключ должен содержать 12–256 печатных ASCII-символов без пробелов; ключи партнёров и управления различаются. Повторная инициализация атомарно обновляет ключи, включая их перестановку, сохраняя ставки и финансовые данные. Конфликт с ключом другого партнёра откатывает оба изменения.

Комиссия хранится в `partners.fee_bps` и фиксируется в invoice при создании. Админского API нет. Например, изменить ставку для будущих счетов alpha:

```bash
docker compose exec postgres psql -U gateway -d gateway \
  -c "UPDATE partners SET fee_bps=150 WHERE name='alpha';"
```

Это 1,5%; существующие invoices сохраняют прежнюю ставку. Сценарий ниже рассчитан на исходные 100 bps.

Вне Compose приложение принимает DATABASE_URL либо PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/PGSSLMODE. DATABASE_URL имеет приоритет; отдельные параметры безопасно кодируются, включая спецсимволы пароля. Без URL обязательны host, user и database; port — 5432, sslmode — require. В Compose используется disable для локальной БД.

## Счёт и зачисление

Проверьте готовность, затем создайте счёт на 100 USDT:

```bash
curl -i http://localhost:8080/readyz
curl -i http://localhost:8080/invoices \
  -H 'X-API-Key: local-alpha-key' \
  -H 'Idempotency-Key: demo-low' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"100.000000","currency":"USDT"}'
```

Ответ 201 содержит `id`, `deposit_address`, сумму, ставку, `status=OPEN` и время создания. Подставьте ID и адрес из ответа:

```bash
invoice_id='ID-ИЗ-ОТВЕТА'
deposit_address='АДРЕС-ИЗ-ОТВЕТА'
curl -i http://localhost:8080/mock/transfers \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' \
  -d "{\"tx_hash\":\"0x1111111111111111111111111111111111111111111111111111111111111111\",\"sender\":\"0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa\",\"recipient\":\"$deposit_address\",\"raw_amount\":\"100000000\"}"
curl -i "http://localhost:8080/invoices/$invoice_id" \
  -H 'X-API-Key: local-alpha-key'
```

`raw_amount` — целые microUSDT: 100000000 = 100 USDT. Через очередной проход сканера появится `payment_status=CONFIRMING`, объект payment с ID, версией наблюдения и числом подтверждений. До обнаружения payment отсутствует. Включение в блок даёт одно подтверждение; N считается как `head_height - payment_height + 1`.

Добавьте два подтверждающих блока и повторите GET после прохода фоновых задач:

```bash
curl -i http://localhost:8080/mock/advance \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' -d '{"blocks":2}'
curl -i "http://localhost:8080/invoices/$invoice_id" \
  -H 'X-API-Key: local-alpha-key'
curl -i http://localhost:8080/balance -H 'X-API-Key: local-alpha-key'
```

Результат: invoice PAID, payment CREDITED. При исходной ставке партнёр получает 99 USDT, доход сервиса — 1 USDT. На чистой БД баланс равен `{"currency":"USDT","available":"99.000000"}`. Обработка асинхронная; краткое состояние AML_PENDING может завершиться до следующего GET.

Повтор создания с тем же ключом и суммой возвращает тот же invoice с кодом 201; `100` и `100.000000` эквивалентны. Другая сумма с тем же ключом даёт 409. Ключи разных партнёров независимы. Повтор `/mock/transfers` с тем же событием не создаёт новый блок или зачисление; изменение данных события даёт 409.

GET чужого invoice с ключом beta возвращает 404; без действующего API-ключа — 401. Суммы API — строки. Нулевая/отрицательная сумма, лишняя точность, выход за int64, неизвестные JSON-поля и неподдерживаемая валюта дают 400; тело больше 4096 байт — 413. Формат ошибки: `{"error":{"code":"...","message":"..."}}`.

## Высокий риск и возврат

Создайте отдельный счёт, подставьте его ID и адрес:

```bash
curl -i http://localhost:8080/invoices \
  -H 'X-API-Key: local-alpha-key' -H 'Idempotency-Key: demo-high' \
  -H 'Content-Type: application/json' -d '{"amount":"100","currency":"USDT"}'
refund_invoice_id='ID-НОВОГО-СЧЁТА'
refund_deposit_address='АДРЕС-НОВОГО-СЧЁТА'
curl -i http://localhost:8080/mock/transfers \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' \
  -d "{\"tx_hash\":\"0x2222222222222222222222222222222222222222222222222222222222222222\",\"sender\":\"0xbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb\",\"recipient\":\"$refund_deposit_address\",\"raw_amount\":\"100000000\"}"
curl -i http://localhost:8080/mock/advance \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' -d '{"blocks":2}'
curl -i "http://localhost:8080/invoices/$refund_invoice_id" \
  -H 'X-API-Key: local-alpha-key'
```

После обработки отправитель из AML_BLACKLIST даёт payment REJECTED и refund READY на все 100 USDT. Invoice остаётся OPEN, комиссия и зачисление отсутствуют. GET показывает ID, сумму, получателя, статус и причину возврата. Баланс после двух сценариев остаётся 99 USDT.

READY обозначает подготовку: актив и обязательство возврата остаются в ledger. Локальная политика считает адреса вне REFUND_UNSAFE_SENDERS безопасными; реальная проверка контрактов/бирж не моделируется. Небезопасный источник, нулевой адрес или REFUNDS_ENABLED=false дают HELD. Для проверки измените конфигурацию, пересоздайте gateway через `docker compose up -d` и создайте **новый** invoice и перевод с новым tx_hash.

Подтвердить проверенный маршрут для HELD, используя ID возврата из GET:

```bash
curl -i http://localhost:8080/mock/refunds/REFUND-ID/approve \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' \
  -d '{"recipient":"0xcccccccccccccccccccccccccccccccccccccccc"}'
```

HELD меняется на READY без новых проводок. Повтор с тем же получателем идемпотентен; другой маршрут для READY даёт 409.

## Недоступность AML, реорг и рестарт

На новом платеже отключите AML **до набора N**:

```bash
curl -i http://localhost:8080/mock/aml \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' -d '{"unavailable":true}'
```

После N сохраняются AML_PENDING, холд полной суммы и задача с датой следующей попытки; доступный баланс не растёт. Тот же запрос с `false` восстанавливает AML; обработка продолжится после задержки повтора. HTTP-переключатель действует в текущем процессе; после рестарта доступность берётся из AML_UNAVAILABLE.

До N можно откатить последний блок с новым переводом:

```bash
curl -i http://localhost:8080/mock/reorg \
  -H 'X-Mock-Key: local-control-key' \
  -H 'Content-Type: application/json' -d '{"depth":1}'
```

Payment становится ORPHANED с новой версией и нулём подтверждений. Если холд уже был создан, реорг атомарно отменяет его и AML-задачу. Повторите исходный `/mock/transfers`: сохраняется payment_id, создаётся новое наблюдение. Можно изменить блоковый log_index, сохраняя tx_event_index. Старый AML-ответ не применяется.

Реорг, удаляющий депозит с зачислением или возвратом HELD/READY, получает 409 без изменения цепи. Откат только подтверждающих блоков требует заново проверить N перед AML-решением. `/mock/advance` и `/mock/reorg` принимают 1–100 блоков; genesis откатить нельзя.

```bash
docker compose restart gateway
```

После рестарта повторите создание и GET прежних счетов: ID, финансовый результат и возврат сохраняются. У незавершённой задачи RUNNING повтор возможен после истечения 30-секундной аренды. LOCAL_MOCKS=false отключает `/mock/*`; сканер и обработка сохранённых задач продолжают работать.

## Тесты и миграции

Для Go-команд нужен Go 1.25+, для `-race` — включённый CGO и C-компилятор. В корне есть Makefile; запуск интеграционных тестов на локальном PostgreSQL 16+:

```bash
make postgres
make test-integration
```

Makefile использует стандартный URL Compose, включает CGO для `-race` и отключает кеш результатов. PostgreSQL запускается отдельной командой и остаётся работать с прежним volume. Если БД уже доступна, достаточно `make test-integration`. Для другой БД или изменённых порта/пароля передайте TEST_DATABASE_URL через окружение:

```bash
TEST_DATABASE_URL='postgres://gateway:local-demo-password@127.0.0.1:54329/gateway?sslmode=disable' \
  make test-integration
```

| Команда | Что запускает |
|---|---|
| make test-unit | Unit-тесты без PostgreSQL и без `-race` |
| make test-integration | Только tests/integration, с `-race` и подробным выводом |
| make test | Все Go-тесты, включая интеграционные, с `-race` |
| make vet | go vet |
| make check | Все Go-тесты с `-race`, затем go vet |
| make test-scenarios | Все Bash-сценарии в отдельном временном Docker-project |
| make help | Список команд |

Один тест можно выбрать так: `make test-integration RUN=TestProcessCrashRecoveryBeforeAndAfterFinancialCommit`. RUN — регулярное выражение Go; при его указании выполняются только совпавшие тесты. Пустой TEST_DATABASE_URL для интеграционных целей отклоняется, чтобы случайный пропуск проверок не выглядел успешным прогоном. Процессный тест сам собирает бинарник с `-race`, поэтому интеграционному пакету также нужен C-компилятор.

Эквивалентная полная проверка напрямую через Go:

```bash
docker compose up -d postgres
TEST_DATABASE_URL='postgres://gateway:local-demo-password@127.0.0.1:54329/gateway?sslmode=disable' \
  CGO_ENABLED=1 go test -race -count=1 ./...
go vet ./...
```

Скорректируйте URL при изменении порта или пароля; спецсимволы в URL требуют percent-encoding. Без TEST_DATABASE_URL команда `go test ./...` запускает unit-тесты, а интеграционные проверки пропускаются. Тесты создают отдельные временные схемы и удаляют только их; пользовательские данные не очищаются. Пользователю БД нужны права создания схем и объектов.

Проверяются точность и денежные границы, комиссии, API-идемпотентность и изоляция, обе финансовые ветки, недоступность AML, конкуренция, lease/version, оба порядка гонки с реоргом, SQL-откаты и балансировка. Отдельный тест собирает бинарник с `-race`, принудительно останавливает процесс до финансового commit, ждёт реального истечения аренды и проверяет восстановление. Повторная остановка после commit сохраняет единственный кредит и возврат; этот тест добавляет около 30 секунд к прогону.

### Bash-сценарии

Для проверки работающего сервиса через HTTP и SQL нужны Bash 3.2+, curl, jq и Docker Compose. Общий запуск собирает образ, создаёт отдельный Compose-project с пустой БД и случайными портами, выполняет проверки и удаляет только созданные им контейнеры, volume и тег образа. Основной project и его данные сохраняются. Настройки сценариев фиксированы: N=3, alpha=1%, beta=2,5%, AML retry=1s; `.env` не используется.

```bash
./scripts/run-all.sh
# Только выбранные проверки, также в новом временном окружении:
./scripts/run-all.sh 03-aml-outage.sh 04-reorg.sh
```

| Файл в scripts/ | Проверки |
|---|---|
| 01-payment.sh | N подтверждений, net/fee, повтор перевода, 1 microUSDT и округление |
| 02-refunds.sh | HIGH → READY/HELD, полный возврат, подтверждение маршрута и конфликты |
| 03-aml-outage.sh | Холды при сбое AML, отсутствие частичного решения, восстановление |
| 04-reorg.sh | Откат до N и с холдом, отмена старого задания, reinclusion и защита окончательного депозита |
| 05-restart.sh | Рестарт процесса, сравнение всех строк 15 таблиц, идемпотентность и возврат |
| 06-api-validation.sh | Конкурентное создание, изоляция, авторизация, JSON, UUID и денежные границы |
| 07-ignored-transfers.sh | Неподходящие события, переполнение raw-суммы и второй независимый перевод |
| 08-balance-limit.sh | Точный MaxInt64, переполнение баланса с сохранением холда; другой партнёр продолжает работу |

Каждый сценарий завершается ненулевым кодом при несовпадении HTTP-кода, состояния или суммы. Асинхронные результаты ожидаются до таймаута (`WAIT_SECONDS`, по умолчанию 30). После каждого сценария SQL проверяет балансировку всех операций и диапазоны счетов. Выбранные файлы запускаются без повторов в порядке таблицы; отдельно их запускает `run-all.sh`. Путь к временным логам выводится в конце, включая ошибочный прогон. Bash-проверка рестарта останавливает сервис штатно; аварийное завершение до commit и гонки с устаревшим worker проверяются Go-тестами.

Миграции 001–003 встроены в бинарник; каждая применяется транзакционно, конкурентный запуск защищён advisory lock. Новые изменения схемы оформляются следующей миграцией. Для ручного управления:

```bash
go install github.com/pressly/goose/v3/cmd/goose@v3.27.0
export GOOSE_DRIVER=postgres
export GOOSE_DBSTRING='postgres://gateway:local-demo-password@127.0.0.1:54329/gateway?sslmode=disable'
goose -dir migrations status
goose -dir migrations up
```

`goose -dir migrations down` удаляет таблицы соответствующей версии: применяйте только к БД, данные которой можно удалить, при остановленном приложении. Приложение автоматически выполняет только Up.

## Устройство и ограничения

- Один Go-процесс обслуживает API, сканер и payment worker. PostgreSQL хранит счета, источник блоков, курсор, наблюдения, задания и ledger. Внешний брокер не нужен.
- Domain-модули: partner, invoice, chain, payment, aml, refund, ledger и money. `internal/httpapi` содержит DTO/HTTP, `internal/postgres` — SQL/транзакции, `internal/app` — запуск и фоновые циклы.
- Один invoice принимает один полный перевод. Сканер закрепляет первый подходящий перевод в порядке блоков/логов. Недоплаты, переплаты и остальные независимые переводы сохраняются в цепочке, но не обрабатываются и не возвращаются. Закрепление переживает реорг и рестарт; доплаты и сроки оплаты исключены.
- Сканер проверяет Ethereum chain_id=1, официальный контракт USDT, Transfer и успешный receipt. Raw-суммы допустимы до uint256; выход за int64 пропускается с предупреждением. Для отрицательных проверок `/mock/transfers` принимает token_contract, topic0 и receipt_success. `finalized` не моделируется.
- USDT — int64 в microUSDT, доменные суммы — BIGINT. Общая сумма ledger — NUMERIC(78,0) с ограничением USDT; умножение комиссии использует big.Int. Комиссия округляется вниз: floor(gross × bps / 10000).
- Ledger разделяет актив, холд, долг партнёру, доход и долг по возврату. Баланс рассчитывается из проводок; каждая операция сбалансирована и неизменяема. Финансовые изменения и статусы фиксируются вместе; корректировки требуют новых операций. Go проверяет диапазоны и блокирует счета в порядке UUID, затем читает свежие балансы. Прямой административный SQL может обойти эти правила; БД сохраняет PK, FK, UNIQUE и CHECK, пользовательских триггеров нет.
- AML вызывается вне транзакции с таймаутом 5 секунд. Задачи имеют аренду и версию; устаревший владелец или наблюдение не применяют решение. Переполнение баланса сохраняет холд и отложенный повтор с кодом balance_limit, позволяя другим задачам продолжать работу.
- Депозитные адреса тестовые, без приватных ключей. ETH, RPC, газ, подпись/отправка транзакций, глубокие компенсации, выводы, outbox, вебхуки и UI не реализованы.

## Как я использовал AI

AI помог подготовить и отревьюить дизайн, реализовать сервис и проверки. В дизайне первоначальное зачисление недоплаты заменено холдом до оплаты: иначе было неясно, что делать с «97 из 100», когда товар не выдан.

В коде первоначально смешивались HTTP-модели, SQL и генерация адресов; после ревью они разделены. Первый симулятор содержал лишние бизнес-правила — после сверки с условием оставлены три операции над цепочкой, обнаружение перенесено в сканер. Блоковый log_index оказался нестабильным при реорге: идентификатором стал tx_event_index внутри receipt. Чтение вершины после ожидания блокировки выделено в отдельный SQL-запрос для свежего снимка.

Ревью выявило ошибку перестановки API-ключей и несовместимость слишком коротких Go-длительностей с PostgreSQL interval; исправления покрыты регрессионными тестами. Финансовая корректность проверяется на настоящем PostgreSQL, через HTTP, конкурентные транзакции и остановку отдельного процесса перед commit и после него.
